# CH78-MAX-001 — server archive intake

Status: implementation prepared for review, **not deployed and not subscribed to MAX**.
Target: existing Supabase `fnwpkmjjdhflnqghnogj` only. Base: `e999eb5af8117d2aa2e5eef52520680bb773b491`.

## Scope and acceptance

Accept authenticated MAX `message_created` notifications for the configured group.
Persist text, sender, creation/event timestamps, attachment metadata, linked message,
and original Message JSON. The archive is backend-only. Existing site tables,
frontend and `story-assistant` are not changed. There are no AI calls, responses
in MAX, scheduled jobs, history import or attachment downloads in this stage.

Acceptance after deployment: a message arrives with the Mac off; 20 redeliveries
produce one row; no success acknowledgement before commit; invalid secret cannot
write; a different group is ignored; neither anon nor a logged-in website user
can read/write the archive. Raw message JSON may contain signed attachment URLs:
do not expose this table or diagnostic payloads to the public client.

## Implementation

- `supabase/functions/ch78-max-webhook/index.ts`: Deno entry point.
- `handler.mjs`: bounded JSON body (256 KiB, 5 seconds), secret verification,
  allowlisted group, safe-integer IDs, insert via PostgREST (8-second timeout).
- `supabase/config.toml`: only this webhook has `verify_jwt=false`; authentication
  is instead the mandatory MAX shared-secret header, checked before reading data.
- Migration generated by `supabase migration new ch78_max_ingest` (CLI 2.58.5).
  Adds **one new table and index**, explicit grants and forced RLS, no client policies.
  The service role has SELECT/INSERT only on this table. No SECURITY DEFINER RPC.
- Composite PK `(chat_id,message_id)` and `ON CONFLICT DO NOTHING` prevent races.
  In case the client times out after a committed insert, a later retry is harmless.
- Forward-only messages with `body=null` and no native mid receive a visibly
  synthetic `forward-only:<sha256>` ID from canonical source content and event
  timestamp. Byte-identical event redelivery and key reordering deduplicate.
  Two completely identical forward-only events at identical timestamps cannot be
  distinguished without an upstream ID; no native MAX ID is fabricated.

HTTP: 200 after commit (also for explicitly ignored event/group), 403 wrong secret,
400 malformed event, 408 slow request, 413 oversized body, 415 wrong media type,
503 disabled/misconfigured/database failure. No message text, key or upstream
error is returned in responses or written to application logs. No public GET API.

Only subscribe to `message_created` in this stage. Edits/deletions are ignored,
so this is a new-message archive, **not an up-to-date mirror of edits/deletions**.
Duplicate create notifications never overwrite the first saved message.
The existing local archive is not automatically uploaded by this change.

## Configuration and deployment — pending owner acceptance

The function stays disabled unless `CH78_MAX_INGEST_ENABLED=true` is set.
Server-only configuration:

- `CH78_MAX_WEBHOOK_SECRET`: random 32–128 ASCII letters/digits/`_`/`-`.
- `CH78_MAX_CHAT_ID`: `-78143291213122` for the currently agreed test group.
- `CH78_MAX_INGEST_ENABLED`: explicit `true` once storage is ready.
- Supabase-provided `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`.

Do not commit real secret values. No MAX bot token or OpenAI key is required by
this receiving function. MAX bot token is only needed by the owner when setting
up the subscription, and must not be pasted into chat or a command history.

Deployment sequence:

1. Review the diff, confirm current target/schema, back up the existing database.
2. Apply only this migration after checking remote migration history: the repo
   does not contain every historical live migration, so do not bulk `db push`.
3. Deploy `ch78-max-webhook` with JWT verification disabled ONLY for this function.
4. Store server configuration through a secure secret-entry mechanism.
5. Confirm wrong-secret rejection and persistence with synthetic requests.
6. With explicit approval, register the HTTPS subscription for `message_created`
   with the same secret. Check existing subscriptions first: enabling webhook
   affects long polling; never replace another bot's subscription.
7. Send one agreed live test message and validate persistence with the Mac off.

At deployment, recheck MAX compatibility with the actual Supabase HTTPS endpoint,
including TLS and cold-start timing. Supabase announced removal of obsolete CBC
TLS suites no earlier than 2026-11-10: verify live MAX handshake, not only curl.
This receiver never calls the MAX API, so the MAX outbound Russian-root CA issue
is not exercised here; future send/history modules require separate TLS checks.

Rollback: unsubscribe the exact new webhook (requires explicit approval), set
`CH78_MAX_INGEST_ENABLED=false`, preserve archived data. Do not drop the table
or modify existing site functions as routine rollback. Disabling intake while a
subscription is active causes retry/error delivery, so do not leave that state
unattended (MAX documents automatic unsubscribe after sustained failures).
