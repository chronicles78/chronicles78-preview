# Читальный зал Хранителя — первая версия, не опубликована

## Что подготовлено

В `keeper/` — настоящий интерфейс для MAX, а не картинка: три раздела
«Спросить Хранителя», «Поиск по словам», «Как это работает». Ответы и результаты
поиска показываются только в окне приложения. Источники раскрываются карточками,
идентификаторы S1–S8 сохраняются, даты — по Самаре. При недостатке сведений
нет произвольной подборки якобы подтверждающих источников.

Предпросмотр `previews/keeper-miniapp-v1.html` собран из тех же исходников,
полностью автономен, использует три вымышленных сообщения, сеть запрещена CSP.
Условный поиск демонстрации не является проверкой реального качества поиска.
`tools/keeper-miniapp/build_preview.py` позволяет воспроизвести образец.

Мобильные варианты проверены в браузере внутри окон 390 и 320 пикселей;
физические iPhone/Android и MAX ещё не проверены. Основной архив 2–3 тысячи
сообщений не импортирован; 394 сообщения относятся к тестовому чату.

## Архитектура

GitHub хранит интерфейс и код. Статические HTML/CSS/JS размещаются по HTTPS;
конкретный адрес и ветку публикации GitHub Pages необходимо подтвердить перед
установкой. Не выполнять merge PR #7 ради публикации интерфейса без отдельного
согласования. Supabase хранит архив и выполняет новый `ch78-max-miniapp`.
Функция вызывает существующий помощник напрямую внутри своего процесса;
сайт, webhook, worker и режим черновиков при этом не меняются.

Нельзя публиковать frontend и считать это подключённым MAX-приложением:
понадобятся миграция, функция, проверка живого входа/членства и регистрация
адреса в кабинете MAX. Аватар и описание подаются вместе с мини-приложением,
как ранее решил Игорь. Наличие модерации и её результат заранее не гарантируются.

## Доступ и обработка данных

Сервер принимает сырые подписанные `window.WebApp.initData`, проверяет HMAC
по алгоритму MAX (ключ WebAppData), запрещает повторы ключей, срок более часа,
время из будущего более 30 секунд и небезопасные идентификаторы. Доверяет только
подписанному user.id; поля chat/user_id из запроса не определяют архив.
Затем через MAX проверяет токен Хранителя и текущее членство пользователя
именно в тестовой группе. Ошибка проверки закрывает доступ. Проверка членства
выполняется при каждом запросе, включая повторное получение результата.

Токен MAX, service_role и OpenAI key в браузер не передаются. В браузере нет
локального хранения архива, результатов или данных входа; ответы сервера
Cache-Control:no-store, credentials:omit. Статический сайт не содержит архива.
CORS допускает только https://chronicles78.github.io; при выборе другого хоста
необходимо явно изменить серверный ORIGIN и покрыть это проверкой.

Тексты отображаются через textContent, не через HTML из модели/архива. API
не принимает произвольный chat_id и возвращает только текст, автора, дату и
номер источника — без сырых вложений и их ссылок. Для ответов доступны только
процитированные источники; при отсутствии ответа список источников пуст.
Никаких методов публикации сообщений MAX мини-приложение не вызывает.

Вопрос и отобранные сообщения обрабатывает OpenAI — как при /ask. Это указано
на экране. Обычный поиск не вызывает OpenAI. Готовые ответы сохраняются в закрытой
таблице для повторного получения без оплаты; старые записи удаляются при новом
запросе после семи дней (это не ежедневная автоматическая очистка).

## Лимиты и неопределённый результат

По умолчанию оба флага miniapp_enabled и miniapp_ai_enabled выключены.
Для первого включения предлагается отдельный бюджет мини-приложения:
5 вопросов ИИ в сутки НА ВСЮ ГРУППУ (до двух обращений OpenAI на вопрос),
200 поисков по словам на группу. Это дополнительные лимиты к уже действующим
лимитам чат-бота; они не увеличивают его бюджет и не заменяют его.
Сутки считаются по Самаре. Между запросами одного пользователя — 2 секунды,
между его вопросами ИИ — 30 секунд. Неудачные и неопределённые попытки учитываются.

UUID запроса атомарно резервируется в БД и связывается с пользователем и отпечатком
вопроса/режима. Повтор возвращает прежний результат либо статус обработки;
изменённый вопрос под тем же UUID отклоняется. Неподтверждённая попытка после
120 секунд получает статус unknown; автоматического повторного ИИ-вызова нет.
Кнопка «Проверить результат» использует прежний UUID. «Начать новый вопрос»
явно создаёт новый запрос. Потеря результата при перезагрузке окна пока не
восстанавливается: история вопросов и фоновое продолжение — отдельные этапы.

## Установка после утверждения

1. Подтвердить оформление, бюджет и адрес HTTPS-хостинга; подготовить материалы
   регистрации/конфиденциальности для кабинета MAX.
2. Применить 20261023183326_ch78_max_miniapp.sql к проекту fnwpkmjjdhflnqghnogj.
3. Установить функцию с шестью файлами: miniapp/index.ts, handler.mjs, auth.mjs;
   ch78-max-assistant/handler.mjs; ch78-max-worker/max-ca.mjs;
   ch78-max-ui/http.mjs.
   verify_jwt=false: проверка подписи MAX реализована внутри, а не отключена.
4. Сверить исходники, права и доступ на рабочей БД с откатом тестовых записей.
5. Опубликовать только согласованные статические файлы, зарегистрировать
   приложение в кабинете MAX вместе с аватаром и описанием.
6. Включить чтение и согласованный бюджет. Проверить реальный запуск из MAX,
   отказ постороннему и поиск. Платный контрольный вопрос — только по разрешению.

До установки не менялись рабочая БД, функции, бот и сайт.

## Результаты проверки

178 автоматических тестов: 96 Node, 73 PostgreSQL/PGlite, 9 Python; Deno проверил
все четыре функции. Новые проверки охватывают подпись независимой реализацией
Node HMAC, подмену/давность входа, членство/токен, CORS, закрытые права, лимиты,
резервирование запросов, повторное получение, неопределённые исходы, поиск
без OpenAI и выдачу только процитированных источников. Браузером проверены
вопрос, поиск, карточки источников и автономный HTML. На ширине 320px
горизонтальной прокрутки не обнаружено. Это проверки на вымышленных данных
и подставных ответах сети; интеграция с реальным запуском MAX ещё впереди.
